# 对讲机线协议（设备 ⇄ 手机）

本文是 AI Passport 对讲机固件（`feature/openclaw-intercom`）与安卓配套 App
（`ai-passport-openclaw-android` 的 `feature/gateway-adapters`）之间唯一的契约。
设备是 BLE 外设，负责采集语音与显示文本；手机是 BLE 中央端，负责通往 agent
网关的网络链路。任何一侧都可以修改本文件，但**两份仓库必须同一轮一起改**——
分帧是两边保持同步的唯一依据。

固件侧实现刻意与传输解耦：分帧、重组、合并、序号与丢帧统计都是纯逻辑，由主机
测试覆盖；BLE 层只负责搬运字节。

## 角色与传输

| 项 | 取值 |
| --- | --- |
| 设备角色 | BLE 外设、可连接广播、单连接（`CONFIG_BT_NIMBLE_MAX_CONNECTIONS=1`） |
| 手机角色 | BLE 中央端（GATT client） |
| 广播名 | `Passport-XXXX`（蓝牙 MAC 后两字节） |
| 服务 | Nordic UART Service，`6e400001-b5a3-f393-e0a9-e50e24dcca9e` |
| 手机 → 设备 | `6e400002-...`（RX），`WRITE` + `WRITE_NO_RSP` + `WRITE_ENC` |
| 设备 → 手机 | `6e400003-...`（TX），`READ` + `NOTIFY` + `NOTIFY_INDICATE_ENC`，CCCD `00002902-...` |
| 建议 ATT MTU | 247（notify 载荷 `min(mtu - 3, 244)`） |
| 连接间隔 | 由手机协商；一轮对讲期间可申请高优先级间隔，空闲时放宽 |
| 加密 | LE Secure Connections + MITM + bonding，密钥长度 16 字节；所有承载数据的特征都受加密门禁 |

选择 NUS 布局是有意的：通用 BLE 工具和手机无需发明新 profile 就能对接，也让设备
与双机链路、Claude Buddy 移植保持兼容。

音频由设备**经 notify 上行**，控制与文本由手机**经 write 下行**。两个方向共用同一
套分帧，因此一份重组器实现同时服务两侧。

## 帧格式

```text
[0] MAGIC0   0xA5
[1] MAGIC1   0x5A
[2] TYPE     见类型表
[3] FLAGS    见标志位表
[4..5] LEN   payload 长度，大端
[6..] payload
```

帧总长 = `6 + LEN`。magic 不是装饰：早期版本只有 1 字节 type，而 PCM 采样字节大量
等于 `0x01`-`0x04`，只要丢一次 notify，接收端就会把音频字节永久当成帧头。两字节
magic 让虚假对齐的概率降到约 1/65536（按字节偏移计），并且让接收端在丢包后能够
重新同步。

### 类型

| 类型 | 名称 | 方向 | payload |
| --- | --- | --- | --- |
| `0x01` | `AUDIO_PCM` | 设备 → 手机 | `[SEQ:1]` + `int16` 小端单声道 PCM，每帧 1024 字节 PCM |
| `0x02` | `TEXT` | 手机 → 设备 | `[role:1]` + UTF-8 文本，单帧 payload 上限 2048 字节 |
| `0x03` | `CONTROL` | 双向 | UTF-8 JSON 对象，命令或确认 |
| `0x04` | `EVENT` | 设备 → 手机 | UTF-8 JSON 对象 |
| `0x05` | `AUDIO_OPUS` | 设备 → 手机 | `[SEQ:1]` + 一个 Opus 包，payload 上限 512 字节 |
| `0x06` | `TTS_OPUS` | 手机 → 设备 | `[SEQ:1]` + `[rate_khz:1]` + `[frame_ms:1]` + 一个 Opus 包，包长上限 `OC_TTS_OPUS_PAYLOAD_MAX`（512）字节 |

`AUDIO_OPUS` 是默认上行路径。`AUDIO_PCM` 仍然实现，作为兜底：编码预算不达标的固件
仍能通话，也能让 App 对着不带编码器的版本做联调。

`TTS_OPUS` 是唯一的下行音频路径，规范见[下行 TTS 音频](#下行-tts-音频)。这个方向
不能用裸 PCM：24 kHz 单声道 16bit 约 48 KB/s，而设备还要同时维持自己的连接。

### 标志位

| 位 | 名称 | 含义 |
| --- | --- | --- |
| `0x01` | `MORE` | 同一逻辑消息还有后续帧 |
| `0x02` | `FIRST` | 多帧消息的第一帧 |
| `0x04` | `LAST` | 多帧消息的最后一帧 |

三个标志位全为 0 表示单帧完整消息。文本使用 `FIRST` / `MORE` / `LAST`；音频帧每帧
可独立解码，边界由 `turn_start` / `turn_end` 事件表达，不用标志位。

## 会话握手

手机完成服务发现、加密、订阅 TX 之后，双方各宣告一次：

```json
{"ev":"hello","proto":1,"caps":["opus","pcm","text","time"],"model":"Passport-3A2B","fw":"0.1.0"}
```

设备在收到通知订阅确认后立即以 `EVENT` 帧发送；手机在写队列可用后以 `CONTROL` 帧
发送同样结构。`proto` 是本文件的整数协议版本。手机在收到设备 hello 之前不得发送
依赖音频的命令；设备只有在**加密完成、订阅完成、hello 交换完成**三件事都做到后才
显示"已连接"。

能力协商刻意做成单向且仅供参考：手机按 `caps` 选择上行编码（有 `opus` 就用
`opus`，否则 `pcm`），并通过 `turn_start` 控制帧回报自己的选择，这样不匹配能在日志
里被看见，而不是静默发生。同一张表也门控下行：有 `tts_opus` 才说明设备实现了
[下行 TTS 音频](#下行-tts-音频)；没有该能力时，手机必须把回复留在屏幕上，而不是
下发 `TTS_OPUS` 帧。

## 音频上行

默认编码是 Opus，与同芯片族的参考语音助手固件一致，也是 ASR 端点能直接接受的格式：

| 参数 | 取值 |
| --- | --- |
| 采样率 | 16000 Hz |
| 声道 | 1 |
| 帧长 | 60 ms（960 samples，1920 字节 PCM） |
| 应用模式 | `OPUS_APPLICATION_VOIP` |
| complexity | 0（更高档位会把 ESP32-C3 算力吃满，语音场景也没有必要） |
| DTX | 开启；静音时可能完全不发包 |
| 预期包长 | 约 40–200 字节，最坏情况按 payload 上限 512 字节处理 |

由此产生的影响贯穿整个设计：

- 上行码率约 3 KB/s，而不是裸 16 位 PCM 的 32 KB/s；MTU 247 下一帧 Opus 正好装进
  一个 notify，热路径上不需要分片与重组。
- 60 ms 帧很小，所以 BLE 链路不必再为带宽让步：对讲期间按低延迟调，空闲时按省电调。
- 丢一个包只损失 60 ms 音频，识别端能容忍。音频永不重传。

采集流水线是：16 kHz I2S 读 → 60 ms 累积缓冲 → 编码一次 → 组一帧 → 一次 notify。
编码在音频任务里完成，编好的帧交给**有界发送环**，由独立发送任务排空，因此再忙的
射频都不会阻塞采集。

`SEQ` 是每个音频帧自增 1 的字节计数，到 256 回绕。它只用于丢帧统计：手机统计缺口并
上报丢帧率，设备统计 notify 失败次数。一轮对讲里丢帧率超过约 1% 就说明编码选择或
连接参数不对，日志必须如实体现，而不是静默劣化。

## 文本下行

`TEXT` 的 payload 首字节是角色：

| 角色 | 含义 |
| --- | --- |
| `U` | 用户语音识别结果（用户说了什么） |
| `A` | 助手回复（网关答了什么） |
| `R` | 预留：以消息形式呈现的系统提示 |

规则：

- 长文本按单帧 payload 2048 字节切分，**绝不切在多字节 UTF-8 序列中间**；设备把
  `FIRST` / `MORE` / `LAST` 合并成一条，收到 `LAST` 才上屏。
- 设备的合并缓冲有上限（2048 字节）；溢出必须上报并截断，不能静默丢弃，更不能截在
  半个字形中间。
- 文本帧可能在音频发送过程中到达。它不得被插进音频 payload：发送方要么把当前音频帧
  发完、要么丢掉它，再写文本；手机侧重组器仍必须处理"半帧音频中间出现插入帧头"的
  情况。
- 文本是可靠方向：用 write-with-response 写入，每帧在 ATT 层得到确认。手机必须把写
  失败当作消息丢失并让用户可见，因为设备屏幕是用户读到答复的唯一地方。

## 下行 TTS 音频

网关回复由设备出声朗读。音频在手机侧合成后以 `TTS_OPUS` 帧推下来；设备自己不调用
语音服务，因此这条下行除了手机已经拥有的网络链路之外，不依赖任何其他云端路径。
播放语义、内存预算与实现计划见
[intercom-tts-playback.zh_CN.md](intercom-tts-playback.zh_CN.md)。

payload：

| 偏移 | 字段 | 含义 |
| --- | --- | --- |
| `0` | `SEQ` | 每帧自增 1、到 256 回绕的字节计数；与上行语义一致，只用于缺口统计 |
| `1` | `rate_khz` | `16` 或 `24` |
| `2` | `frame_ms` | 帧长（毫秒），当前固定 `60` |
| `3..` | Opus 包 | 一个 Opus 包，上限 `OC_TTS_OPUS_PAYLOAD_MAX`（512）字节 |

规则：

- 帧长与采样率随**每一帧**一起下发，因此任何逐帧元数据都不依赖历史。流中途改变采样率
  是合法的：设备为新速率重新初始化解码器，从下一帧继续，而不是继续按旧速率静默地
  播错。
- payload 总长为 `3 + 包长`，即 `4`–`515` 字节。声明长度不在该范围内即视为损坏，
  按重新同步规则处理，而不是当作解码错误。
- `OC_TTS_OPUS_PAYLOAD_MAX` 取 `512u`，它约束的是 Opus 包而不是整个 payload。固件
  把它与其它载荷上限定义在一起。
- `SEQ` 缺口只统计并上报，绝不要求重传。丢一个 60 ms 的包只是某个字轻微粗糙，不值得
  为此卡住扬声器。
- 实现该路径的设备在 hello 的 `caps` 里带上 `tts_opus`。手机不得向未声明该能力的设备
  发送 `TTS_OPUS`：接收端把未知类型按错位处理，会连带丢掉被拒帧头之后的那一帧。

### 队列与流控

设备是无 PSRAM 的静态内存目标，因此两条队列都是固定深度：

| 缓冲 | 深度 | 作用 |
| --- | --- | --- |
| 解码队列 | 24 包，60 ms 一帧时约 1.44 s | 吸收 BLE 突发与手机调度抖动，不让播放断粮 |
| 播放队列 | 2 块解码后的 PCM | 一块喂 codec、一块在填，解码抖动不会变成静音 |

- 溢出时设备丢**最旧**的那一包并计数。用户在等的是刚合成的语音，所以新音频优先。
- 手机领先设备不得超过约 **2 s**。再往前压，这条有界队列就会开始丢掉语音，比暂停发送
  更糟；手机自行调速，并把 `tts_playback_done` / `tts_playback_aborted` 当作流结束的
  信号，而不是逐帧配额。
- 播放是半双工：设备处于 TTS 播放态时停止上行采集，麦克风不会把扬声器录进去。队列
  排空或收到 `tts_abort` 后立即恢复采集。

## 控制通道

`CONTROL` 的 payload 是 JSON 对象。已定义命令：

| 命令 | 方向 | 含义 |
| --- | --- | --- |
| `{"cmd":"hello","proto":1,...}` | 手机 → 设备 | 握手手机侧 |
| `{"cmd":"turn_start","codec":"opus"}` | 手机 → 设备 | 手机已接受本轮并开始识别 |
| `{"cmd":"time","epoch":<秒>}` | 手机 → 设备 | 校准状态栏显示的时间 |
| `{"cmd":"clear_display"}` | 手机 → 设备 | 清空对话区 |
| `{"cmd":"status"}` | 手机 → 设备 | 请求设备状态（电量/音量/麦克风增益/链路），供 App 控制台显示 |
| `{"cmd":"audio","volume":<百分比>,"mic_gain_db":<数值>}` | 手机 → 设备 | 设置输出音量与麦克风增益；两项均由 App 主导 |
| `{"cmd":"gateway","state":"ready"\|"connecting"\|"working"\|"offline","detail":"<文本>"}` | 手机 → 设备 | 上报手机侧网关状态，供设备分开显示设备与网关两种状态。状态词与手机端共用：`ready`、`connecting`、`working`（已连上、agent 正在跑）、`offline`；非 `ready` 时 `detail` 携带可读原因或进度阶段；未知状态按 `offline` 处理 |
| `{"ev":"tts_start"}` | 手机 → 设备 | 手机即将推送 TTS 音频；设备进入播放态，暂停上行采集，并保持背光，让用户能看着回复逐字出来 |
| `{"ev":"tts_stop"}` | 手机 → 设备 | 不会再有新音频；设备把已入队音频播完后退出播放态 |
| `{"ev":"tts_abort"}` | 手机 → 设备 | 立即丢弃队列：用户重按 `OK`、App 侧打断，或网关流中断。采集可以立刻恢复 |
| `{"ev":"turn_ready"}` | 手机 → 设备 | 手机侧录音与识别已真正就绪，从现在起用户说话会被识别；设备据此把轮次指示变绿。它承载在 `CONTROL` 帧里，采用事件形状是因为它报告手机观察到的事实，而不是要求设备执行的命令 |

未知命令必须忽略而不是报错，这样新版手机可以对接旧版设备。

设备自己连不上网关（网关在手机上），所以由手机上报。设备状态栏因此有两行：BLE
链路状态与最近一次上报的网关状态。只有两者都就绪时，状态栏才收敛为单个「就绪」；
否则分别标出哪一侧没就绪，且网关不可用时把它的 `detail` 顶到底部提示行，保证原因
读得全。手机必须在握手完成后上报一次，之后每次状态或原因变化再上报；在首次上报
之前，设备把网关显示为「未知」，不做推测。

`turn_ready` 是设备轮次反馈的另一半：设备无法知道手机侧的录音与识别是否真正在听，
所以把它当作「现在可以说话了」的信号，而不是靠猜。设备界面因此是：按下 `OK` → 屏幕
立刻变红（`已按下，准备中…`）；收到手机的 `turn_ready`，或 2.5 秒兜底超时仍未收到，
→ 屏幕变绿（`可以说话了`，此时说话会被采集）；松开 `OK` → 本轮结束、恢复正常界面。
始终不发 `turn_ready` 的手机只会退化到兜底超时，不会坏掉。

## 事件

`EVENT` 的 payload 是 JSON 对象。已定义事件：

| 事件 | 含义 |
| --- | --- |
| `{"ev":"hello",...}` | 握手设备侧，每次订阅成功发送一次 |
| `{"ev":"turn_start"}` | 用户按下对讲键，后续为音频帧 |
| `{"ev":"turn_end","frames":<n>,"codec":"opus","dropped":<n>}` | 用户松开对讲键，手机可以结束识别 |
| `{"ev":"status","battery":<百分比>,"volume":<百分比>,"mic_gain_db":<数值>,"link":"ready"}` | 设备状态快照，也会在被请求时以及任一项变更后发送 |
| `{"ev":"error","code":"<code>","detail":"<text>"}` | 设备侧故障，值得在 App 控制台显示 |
| `{"ev":"tts_playback_done","frames":N,"decoded":D,"dropped":X,"underruns":U,"decode_us_max":M}` | 设备播完一条 TTS 流；`frames` 是收下的包数，`decoded` 是解码成功的包数，`dropped` 是被丢弃的包数（队列溢出 + `SEQ` 缺口），`underruns` 是播放时无解码数据可用的次数，`decode_us_max` 是单包最长解码耗时（微秒） |
| `{"ev":"tts_playback_aborted"}` | 设备因 `tts_abort` 或解码连续失败而丢弃了本条 TTS 流的剩余部分 |

`turn_end` 是结束一轮的**唯一**信号。手机绝不能从音频帧之间的间隔推断"说话结束"，
因为 DTX 造成的静音本来就不发包。

## 可靠性、背压与丢帧统计

音频没有应用层确认，也不需要有。让流水线保持诚实的是下面几条：

- 设备：发送环有界。射频不可用、积压或返回无缓冲时，该帧被丢弃、计数加一，并在下一次
  `turn_end` 里上报该计数。采集永远不因射频而阻塞。
- 设备：文本帧由手机以 with-response 写入，失败即视为丢失；手机应在短暂延时后重试
  一次，仍未成功就在自己的界面标注"未送达"。
- 手机：收到的 notify 字节立即拷贝进队列，由单一 worker 处理，绝不在 BLE 回调里做
  重活。
- 手机：开始新一轮对讲时清空已入队但未发送的文本帧，避免用户重新开口后旧回复才上屏。
- 设备：`TTS_OPUS` 帧永不重传。溢出时丢最旧的包，并在 `tts_playback_done` 里上报实际
  解码与播放的数量，使「已发送」与「已听到」始终可区分。
- 手机：`tts_start`、`tts_stop`、`tts_abort` 用 write-with-response 写入，因为它们
  包裹一条流、与音频的先后顺序有意义；`TTS_OPUS` 音频帧用 write-without-response
  写入，避免音频速率每帧都付一次 ATT 往返。

## 重新同步

接收端把输入当作字节流，必须能从下面三种情况恢复：

1. 一次 notify 末尾的半截帧（正常情况）。
2. 丢失一次 notify，导致帧中间出现空洞。
3. 一个帧头被插进另一个帧的 payload 中间。

恢复规则：

- 等帧头时向前扫描 `0xA5 0x5A`，随后要求 type 合法、长度能装进重组缓冲；任何不满足
  的情况都只前进一字节继续扫描。
- 攒 payload 时同样扫描插入的帧头。判据刻意收窄：候选帧必须有合法 type、合理长度，
  且不能是"音频帧里再嵌音频帧"。命中即丢弃半截帧，从候选处重新开始。
- 重组缓冲必须能容纳最大合法帧（`6 + 2048`）；声明长度超过该值的帧一律按损坏处理。

## 配对与安全

- 配对由手机发起。设备显示随机 6 位密码，手机弹框输入后调用 `setPin` 与
  `setPairingConfirmation`。
- 显示的密码必须 ≥ 100000。带前导零的取值在 Android 侧会在 confirm/random 交换阶段
  失败，而换 Linux 中央端却能配对成功——正因为它只在真机暴露，才必须写在这里。
- bonding 存 NVS，因此重连无需再次弹框。NVS 必须在射频启动前初始化，否则 PHY 每次
  开机都要重新做校准。
- 每个特征都必须有 access callback，包括只做 notify 的那条；缺回调会让服务注册失败，
  而错误信息看起来像内存分配失败。
- 由于所有承载数据的特征都受加密门禁，未加密到达的写入必须被拒绝而不是被处理。

## 版本

hello 里的 `proto` 就是本文件的版本号。不兼容的改动必须提升版本，并在同一次发布里
两端一起实现。增量改动（新增事件、新增控制命令）不提升版本；接收端忽略自己不认识
的内容。

## 刻意否决的方案

- **只用裸 PCM 上行。** 能用，但 256 kbps 没有给射频重传留任何余量，而且会把连接
  参数逼到"音质取决于手机型号"的角落。现在只作为兜底。
- **每个方向再加一条特征。** 两条特征已经覆盖两个方向；按消息类别拆分只会让 GATT
  表膨胀，而帧类型已经承担了这件事。
- **音频加应用层 ACK。** 60 ms 语音不值得一次往返；识别端对缺口的容忍度高于一次停顿。
- **两字节或更长的序号。** 在这个速率下 1 字节足够发现丢帧；序号是诊断工具，不是投递
  保证。

## 测试钩子

- 分帧、重组、文本合并、序号统计与 turn 状态都是纯逻辑，两端都应进主机测试；安卓侧
  以 JVM 单测镜像同一批用例。
- 主机侧 BLE 对端（Python + `bleak`）可以不接手机就对真机讲这套协议，是复现分帧问题
  最快的手段。
- 设备侧每轮重算的丢帧率与编码耗时是两个必须打印的数字；判断 Opus 路径在本芯片上能
  不能站住，就靠它们。

## 设备按键（仅供参考）

不属于线协议，但 App 侧的实现不得与之矛盾：

| 操作 | 行为 |
| --- | --- |
| 按下 `OK` | 点亮屏幕并在按下瞬间开始一轮：屏幕立刻变红（`已按下，准备中…`），随后收到手机的 `turn_ready` 或 2.5 秒兜底超时后变绿（`可以说话了`）；音频帧持续上行直到松开 |
| 松开 `OK` | 结束本轮；手机侧收尾识别；恢复正常界面 |
| 长按 `UP` | 打开设备设置页（设备信息 / 亮度 / 返回） |
| `UP` / `DOWN` | 浏览对话历史（由新到旧）；在设置页内则移动高亮或步进数值 |

输出音量与麦克风增益在设备上不可调，由 App 通过 `audio` 控制命令下发；亮度保留
设备本地调节，使设备脱离手机时仍可用。

## 已定与待定

已定：

- `status` **按需拉取**。设备在背光熄灭后仍保持供电与连接，手机随时可以拉取状态，因此
  不做周期心跳；设备在自身配置变更后仍主动补一次 `status`。
- 音量与麦克风增益由 App 主导：通过 `audio` 控制命令下发，并在 `status` 中回显。亮度
  保留设备本地调节，设置页只留设备信息、亮度与返回。

仍待定：
- PCM 兜底路径每帧 1024 字节 PCM 的取值继承自参考固件，在 Opus 成为默认之后没有重新
  实测过。
